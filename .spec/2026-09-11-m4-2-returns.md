# Spec: M4.2-returns — Cancelaciones y devoluciones (#24)

**Status**: APPROVED · **Spec ID**: 2026-09-11-m4-2-returns
**Issue**: #24 · **Branch**: `feat/f4` · **Depends**: M4.1

---

## Objetivo

Solicitar cancelación/devolución desde el detalle del pedido (solo en estados permitidos) y listar devoluciones del cliente.

## Contratos (auth:sanctum)

- `POST /orders/{orderNumber}/returns` body `{ reason: string ≤255 (req), description?: string ≤2000 }` → `201 { message, data: ReturnRequest }`.
- `POST /orders/{orderNumber}/cancellations` body igual → `201 { message, applied: bool, data: ReturnRequest }`.
- `GET /return-requests?per_page=` → paginator de `ReturnRequest`.
- `ReturnRequest`: `id`, `folio`, `type` (`return`|`cancellation`), `orderNumber`, `orderStatus`, `reason`, `description`, `status`, `resolutionNotes`, `createdAt`, `resolvedAt`.

### Reglas backend (autoridad)

- **Devolución**: no permitida si el pedido está `cancelled` o `pending` (`createReturn` → 422).
- **Cancelación**: `cancelled` → 422; `shipped`/`delivered` → requiere flujo proveedor; `pending`/`paid` → puede aplicar directo (`applied=true`).
- Errores: `403` (no dueño), `409` (solicitud abierta duplicada), `422` (estado/motivo inválido) — **nunca** mostrar como éxito.

## Arquitectura

- `order.model.ts`: `ReturnRequest`, `ReturnType`, `ReturnStatus`.
- `order-service.ts`: `getReturnRequests(page?)`, `requestReturn(orderNumber, {reason,description})`, `requestCancellation(orderNumber, {reason,description})`.
- `order-store.ts`/hooks: `returns`, `submitReturn`, `submitCancellation`, estado por acción (`idle|submitting|error|success`), anti-doble-submit.
- UI:
  - Detalle de pedido: acciones **solo** si el estado lo permite (cancelar si no `cancelled`; devolver si no `cancelled`/`pending`).
  - Modal/pantalla `src/app/orders/request.tsx` con motivo (select o texto) + descripción.
  - `src/app/returns/index.tsx` (lista de devoluciones con estado real).
- Registrar rutas en `_layout`.

## Seguridad

- Auth obligatoria; mensajes de error del backend tal cual (no inventar éxito).

## Escenarios BDD

- **AC1**: cancelar en estado `paid` → `requestCancellation` llamado; `applied=true` muestra "Pedido cancelado".
- **AC2**: devolver en `cancelled`/`pending` → acción **oculta/deshabilitada**; no se llama el service.
- **AC3**: `reason` vacío → validación, no se envía request.
- **AC4**: `403`/`409`/`422` → estado de error con mensaje; sin marcar éxito.
- **AC5**: lista `/return-requests` paginada muestra `folio`, tipo y `status`.
- **AC6**: anti-doble-submit: un submit en curso deshabilita el botón (una sola llamada).
