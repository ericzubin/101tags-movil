# Spec: M6.1-profile — Perfil, settings y logout (#29)

## Objetivo

Pantalla de perfil con datos reales (`/auth/customer/me`), settings mínimos y logout que invalida backend + limpia storage.

## Contratos (auth:sanctum)

- `GET /auth/customer/me` → `{ user: { id, name, email, phone, role } }`.
- `POST /auth/customer/logout` → `{ message }` (invalida token Sanctum).
- Logout local: `SecureStore.deleteItemAsync('auth.token')` + `('auth.user')` (ya implementado en `auth-service`/`auth-store`).

## Arquitectura

- `auth-service.ts`: `getMe()` → `GET /auth/customer/me` (si no existe).
- `auth-store.ts`: `refreshUser()` que actualiza `user` con la respuesta; `logout()` ya existente (backend + limpieza). No exponer token en UI.
- UI: `src/app/profile.tsx` (o contenido de `(tabs)/account.tsx`): nombre/email/teléfono/rol, sección settings (versión de app vía `expo-constants` si ya está disponible — sin deps nuevas; si no, omitir), accesos a Términos/Privacidad/Ayuda, botón **Cerrar sesión** con confirmación → `logout()` → `router.replace('/(auth)/login')`.
- Settings no muestra token ni datos técnicos sensibles.

## Seguridad

- Nunca renderizar/loggear token. Logout debe limpiar storage incluso si el backend falla (comportamiento actual de `auth-store`).

## Escenarios BDD

- **AC1**: al abrir perfil, `refreshUser()` llama `GET /auth/customer/me` y muestra `name/email/phone/role`.
- **AC2**: error de red en `/me` conserva el `user` cacheado y muestra error no bloqueante.
- **AC3**: logout con confirmación → `authService.logout()` (POST) y luego limpia token/user (SecureStore).
- **AC4**: si el POST de logout falla, el estado local igual queda sin sesión (limpia storage) y redirige.
- **AC5**: perfil no muestra el bearer token ni secretos.
